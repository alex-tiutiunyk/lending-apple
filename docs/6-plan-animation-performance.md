# Plan 6: animation performance

Builds on `0-plan-landing.md` … `5-plan-hover-and-play.md`. Where this plan conflicts with an earlier one, this plan wins (plan-order note in plan 0). Everything not mentioned here keeps the earlier rules: no animation library, one rAF loop (`frameLoop.ts`), visible without JS, all copy in `content/`, components under 150 lines, BEM class names, motion levels `full` / `calm` / `off` through the plan 3 mixins and hooks, lazy chunks for what most visits never see.

Goal: every scene at 60 fps on a laptop and a steady frame on a phone, with the work moved off the main thread wherever the browser can take it: scroll positions drive the compositor instead of style recalcs, continuous loops run on GPU layers, the finish change stops restyling the whole page, and nothing reads layout after something else wrote it in the same frame. Nothing here is built yet; everything is measured first (§1) and measured again after each step (§13).

About "layers": the layers that matter for speed are **compositor layers** (one GPU texture per promoted element, moved and faded without repainting), not CSS cascade layers (`@layer`), which only order the cascade and change nothing about rendering. This plan budgets compositor layers (§9) and uses no `@layer`.

Forced layouts (a read after a write in the same frame), per the stacks:

- Pip's tick reads `offsetWidth` every frame right after the previous tick wrote `--pip-x` (`useMascotBrain`): 150–200 forced style + layout passes per 2.5 s at idle, 2–3.5 ms each.
- `useMascotAvoidance.onScroll` → `checkStanding` → `visibleTargets` reads `getBoundingClientRect` of every interactive element in the zones in view on **every scroll frame**, after the frame's writes: 82 forced recalcs of 60–120 ms in the scroll trace (each one pays for the frame's `<body>` writes).
- `escapeRunner.step` reads the block rect and every letter's home rect per tick, and `pipRect()` (`escapeChase.ts`) queries and measures Pip per tick, after Pip's own write.
- `pullMagnetic` and `trackSurface` (`usePointerHover`) measure the element on every pointer frame after writing `--pull-*` / `--mx` `--my`.
- `settledBlocks` (`escapePlanner.ts`; `isSettled` in `letterWrap.ts` = `getComputedStyle` ×2 + rect per block) runs from the heading poll after writes.
- `useBirdLife.onPointer` reads the render's rect on every pointer frame while a bird is perched, then writes `rotate` on both heads.

Continuous animations that fail to composite (Chromium `Animation` trace events; the bits decode through `compositor_animations.h`): Pip's walk step and bob (`rotate` / `translate` on `<g>`: `kSVGTargetHasIndependentTransformProperty` + `kTargetHasInvalidCompositingState`), both living marks (`scale` on the root `<svg>`, `rotate` on the leaf path), the lens bug and email bug legs (`transform` on `<g>`), the bird's wings and head, the footer edge wave (`<g>`) and pulse window (`rect`), the gradient `stop-color` transitions (`kUnsupportedCSSProperty`), the `--accent-*` transitions on `<html>` (`kUnsupportedCSSProperty`), and the hero words (`kTargetHasIncompatibleAnimations`: a `transform` keyframe animation and a `translate` hover transition on the same span). Each costs a style recalc and a repaint of its SVG per frame, around 1.6 ms per frame at idle together.

Layers: 117 compositor layers at the hero, 101 of them drawing, a dozen of them viewport sized (the backdrop root, two blobs 80–90 vmax, two tints, the waves strip, the grain, the canvas, both pinned stages, the overlays), plus one layer per scroll-driven reveal target (every title word, paragraph and card gets its own layer for the life of the page, because a scroll-driven animation never finishes). Chromium tiles picture layers and rasterises only the tiles near the viewport, so a 90 vmax blob costs about one viewport of texture, not its full box; the number that matters on a phone is **overdraw**: at the hero about ten viewport-sized layers are composited for every pixel, four times the pixels on a 2× screen (§9, §14). The main thread also never idles: Pip's walk tick subscribes for the whole visit (holds and still acts included), and the particles keep ticking while a shape is formed, so `requestAnimationFrame` runs at 60 Hz from the first paint to the last (§5).

Sources used for the rules below: [web.dev: animations and performance](https://web.dev/articles/animations-and-performance), [web.dev: compositor-only properties and layer count](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count), [Chrome: hardware-accelerated animations](https://developer.chrome.com/blog/hardware-accelerated-animations), [Chrome: scroll-driven animation performance case study](https://developer.chrome.com/blog/scroll-animation-performance-case-study), [web.dev: `@property` performance](https://web.dev/blog/at-property-performance), [MDN: `content-visibility`](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility), [Chromium: `compositor_animations.h`](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/animation/compositor_animations.h), [Bram.us: width/height animations off the main thread](https://www.bram.us/2025/11/13/animating-css-width-or-height-no-longer-force-a-main-thread-animation-in-chrome-under-the-right-conditions/).

## 2. The rulebook

Rules every later plan inherits. Each has a test or a probe check (§13).

1. **Per-frame values never inherit.** A value written on every frame goes on the element that uses it and is registered with `@property { inherits: false }`, or, better, is written as `transform` / `opacity` / `translate` directly. Nothing per frame on `<html>`, `<body>`, a section or a stage.
2. **Scroll position is a timeline, not a variable.** Anything that follows the scroll position uses `animation-timeline: scroll()` / `view()` with keyframes on `transform` / `opacity` (compositor); JS drives scroll only where the browser lacks `animation-timeline`, and then through Web Animations `currentTime` on the same keyframes.
3. **Reads before writes.** The frame loop runs a read phase, then a write phase. A listener measures in the read phase and queues its DOM writes. Sizes that change only on layout are cached from the layout listener or a `ResizeObserver`, never read per frame.
4. **Loops live on the compositor.** A continuous animation (anything `infinite`, or longer than 2 s) targets an HTML element or a root `<svg>`, animates only `transform` or `opacity`, and does not share the element with a transition on a transform-family property. Individual transform properties (`rotate`, `scale`, `translate`) are for HTML elements only.
5. **No filters on moving things.** `filter`, `backdrop-filter`, `drop-shadow()` and SVG filters never sit on an element whose content or position changes per frame. Glows are gradient elements.
6. **Promote while awake, demote at rest.** `will-change` only under `[data-awake]` / `[data-near]`, removed otherwise. Overlapping content is isolated with `isolation: isolate` and `contain: paint` so promotions stay local.
7. **Skip what is off screen.** Every section is `content-visibility: auto` with an intrinsic size; ambient loops run only `[data-awake]` (plan 1 §1), scroll listeners for a scene only `[data-near]`.
8. **Budgets are measured, not promised.** §14 numbers are checked by `npm run perf` and the `@perf` tests before a plan is called done.
9. **The loop sleeps.** When nothing on screen moves, no `requestAnimationFrame` is scheduled: a tick listener unsubscribes the moment its subject stands still (Pip held or in a still act, particles settled, a count finished) and subscribes again on the next change. Idle means zero rAF callbacks per second (§14).

## 3. The page position: timelines and a scroll bus

### 3.1 `--doc-p` consumers become scroll-driven animations

The four readers of `--doc-p` (`Backdrop.module.scss` blobs and tints, through the `--backdrop-p` alias on the backdrop root, which goes; `Header.module.scss` progress line and its tip) get keyframes on `animation-timeline: scroll(root)` under `@supports (animation-timeline: scroll())`:

- `.blob--high`: `from { transform: translate3d(0, 0, 0) } to { transform: translate3d(-18vw, 22vh, 0) }`; `.blob--low` the mirror.
- `.tint--cool`: `opacity 1 → 0`; `.tint--warm`: `opacity 0 → 1`.
- `.progress-line`: `transform: scaleX(0) → scaleX(1)`; the tip: `translateX(-100%) → translateX(0)`.

`animation-timing-function: linear`, `animation-fill-mode: both`, and the plan 3 gates stay: the backdrop drift runs under `motion-safe` and is `animation: none` at `off` (it stands still as before); the header line follows at every level like a scrollbar (plan 4 §2.1), so it has no gate.

**Fallback** (`@supports not (animation-timeline: scroll())`, Firefox stable at the time of writing): the same keyframes are driven by JS. `useDocumentProgress` stops writing `<body>` and instead sets `currentTime` on each consumer's animation: the consumers carry `data-doc-p`, the hook calls `element.getAnimations()` once per layout and writes `animation.currentTime = progress * 1000` per scroll frame (the animations are declared with `animation-duration: 1000ms; animation-play-state: paused` in the fallback block). Each update restyles one element. No custom property remains. The hook keeps its other job, the one-per-visit `cheer` request to Pip at the end of the page (plan 4 §2.4), which needs the progress number but no DOM write.

### 3.2 `--scroll-v` through a scroll bus

Velocity has no CSS timeline. Its readers (both living marks' lean, the footer edge `scaleY`, the header line tip `opacity`, the `.reels` `skewX` of every stat) register themselves: `useScrollVelocity(ref)` adds the element to a set in `useDocumentProgress`, which writes `--scroll-v` on **each registered element** in the write phase, only while the element or its closest `[data-awake]` ancestor is awake (the marks and the footer edge carry the attribute themselves; the stats' `<dl>` carries it from plan 5 §12 and the reels inside read it; the header tip has no gate, the header is always in view). Because the property is registered `inherits: false`, the write must land on the element whose rule reads it, not on a parent, and not on an element whose `::after` reads it: the tip's `opacity` moves from `.progress-tip::after` to `.progress-tip` itself (a pseudo-element does not inherit a non-inherited property), and each of the four `.reels` registers on its own rather than the `<dl>`. `--scroll-v` is registered in `global.scss`:

```scss
@property --scroll-v {
  syntax: '<number>';
  inherits: false;
  initial-value: 0;
}
```

The marks read it on the HTML `.mark` box that §7 puts around their pieces (today the root `<svg>` carries the lean as `rotate` plus its `transition: rotate` and the `breathe` loop; after §7 the lean and the transition sit on the box, an HTML element, and the loop on a piece). Cost per write: one element plus its subtree (≤ 10 nodes), ~0.1 ms, instead of 85 ms. The velocity keeps ticking for ~0.5 s after a scroll as today, gated as today by `useReducedMotion` only.

### 3.3 Hero parallax and fade

- `--hero-out` moves from the parts layer (179 nodes) to a scroll-driven `opacity` animation on `.parts` and on `.line`: `animation-timeline: scroll(root); animation-range: 0 60svh` (today's fade length is 60 % of the hero's height, which is one viewport minus the header). Fallback as in §3.1.
- `--px` / `--py`: `HeroExtras` writes `translate` directly on each of the seven `.part` elements in the write phase (`${px * depth * 4}px ${py * depth * 4}px`); the `.part` rule loses its `transform` calc and its `transition: transform 400ms` becomes `transition: translate 400ms`. Seven writes of 0.1 ms instead of one write of 5.5 ms. The `part-drift` keyframes (`transform`) then share the element with the `translate` transition; both are transform-family on an HTML element, which Chromium composites together, but if the probe reports `kTargetHasIncompatibleAnimations` on a part, the drift moves to the inner `<svg>` root as in §7.
- The hero line (`.line`) keeps its `--hero-out` fade through the same scroll-driven `opacity` keyframes; the `removeProperty('--px')` cleanup below `md` becomes `translate: none` on the parts.

### 3.4 The Numbers scrub text

`ScrubText` (plan 2 §3) writes `--p` on the intro paragraph on every scroll frame through `useViewProgress` (0 → 1 while the paragraph's top travels from 90 % to 40 % of the viewport height), and every `.scrub-word` computes `--lit` from it (≤ 32 words restyled per frame; a small cost, but a per-frame inherited write all the same, rule 1). Each word gets `opacity 0.5 → 1` keyframes on `animation-timeline: view()` with its own `animation-range` from the existing `nth-of-type` Sass loop (`entry` offsets spread over the same 50 vh window, like the title words' `--word-from` in `RevealTitle.module.scss`), under the same `@supports` split as the `reveal` mixin. `--words` (set once) stays. **Fallback**: `useViewProgress` drives `currentTime` on the paragraph's word animations as in §3.1; the no-JS state (every word lit) stays through the `@supports not` branch, and the `reduced` state keeps the `--p: 1` end values as `animation: none` plus full opacity.

## 4. Pinned scenes on view timelines

Both pinned sections (`LineDraw`, `ExplodedView`) get a named timeline on the section: `view-timeline: --design block` / `--inside block`. Progress 0 → 1 of today's `pinnedProgress` equals the `contain` range of the section's view timeline (the section fully covers the scrollport from its top edge aligned to the top until its bottom edge aligned to the bottom), so every rule that reads `--progress` turns into a keyframe animation on the element that owns the property, with `animation-timeline: --inside` and an `animation-range` in `contain` percentages.

ExplodedView, generated by the existing Sass loops (`$step`, `$window`, `$turn-start`, … and, below `md`, `$compact-step` / `$compact-window` on `data-compact-order`, which get their own ranges in the same loop):

- `.layer[data-order=i]`: `animation: layer-settle linear both; animation-range: contain #{(0.04 + i * $step) * 100%} contain #{(0.04 + i * $step + $window) * 100%}`; keyframes `from { opacity: .55; transform: translateZ(calc(var(--rest-z) + var(--spread))) scale(.94) } to { opacity: 1; transform: translateZ(var(--rest-z)) scale(1) }`. `--eased` (quadratic ease-out) becomes `animation-timing-function: cubic-bezier(0.25, 0.46, 0.45, 0.94)`, adjusted by eye.
- `.layer.slice`: same with the slice offset baked into `--rest-z` per slice.
- `.stack`: `stack-turn` from `rotateX(56deg) rotateZ(-34deg)` to `rotateX(24deg) rotateZ(-14deg)`, range `contain 80% contain 100%`.
- `.shadow`: opacity and scale over `contain 0% contain 100%`.
- Wake and glint (`--wake`, `--glint`): opacity keyframes with ranges `contain 85% contain 91%` and `contain 90% contain 98%` on the elements that use them.
- The three parts per layer (`[data-part-slot]`, `--part-local`, `--part-away`): keyframes on the slot with its own range (`--slot-delay` folded into the Sass loop). They are SVG children, so they stay main-thread (§7 rule), but each restyles one node instead of the stage.
- The labels (`.label[data-order]`, `--landed`): the same way, with `transform` on the label, `transform: scale()` on its `::before` dot and the `color-mix()` text colour as a `color` keyframe (main-thread, one node, a 3 % window).

LineDraw: `--draw-guides` … `--draw-details` become `stroke-dashoffset` keyframes on the outline paths with ranges from `--draw-from` / `--draw-span` (main-thread paint, as today, but scoped to the path); `.outline` opacity and `.render` `clip-path: circle()` become keyframes with the smoothstep as a timing function (`cubic-bezier(0.4, 0, 0.6, 1)` is close). The `clip-path` animation is composited in Chromium builds that ship `CompositeClipPathAnimations` and falls back to the main thread elsewhere; either way only the render restyles.

Sass detail: the `animation` shorthand resets `animation-timeline` and `animation-range`, so every generated rule emits the shorthand first and the timeline and range after it, and `config/scrollRanges.test.ts` (§13) asserts the timeline survives in the compiled CSS.

`useScrollProgress` keeps `data-near` (for `will-change` and the particles) and the `data-stage` geometry for the particle anchors, but stops writing `--p` where `animation-timeline` exists. **Fallback** without `animation-timeline`: the hook writes `currentTime = progress * 1000` on every animation of the section (`section.getAnimations({ subtree: true })`, cached per layout), as in §3.1. The static scene (plan 3 §4, `static-scene` mixin) keeps `animation: none` and the end-state values as today.

The `--p` e2e assertions (`runtime.spec.ts`, `smoke.spec.ts` and `a11y-panel.spec.ts` all read `style.getPropertyValue('--p')` on a section) change to read the first layer's animation `currentTime` / `effect.getComputedTiming().progress` through `getAnimations()`, which works in both branches; the static-scene assertions (`--p` = 1 at `off` and large text) read the same way, where the animation is `none` and the end state is the computed style.

## 5. The frame loop: read, then write

`frameLoop.ts` grows two phases. Every listener type (`scroll`, `pointer`, `tick`) runs in the read phase and gets a `write(fn)` parameter (or returns a function) that the loop calls after all listeners, in order. Writes queued during the write phase run in the same flush. `documentTop` and friends are read-phase helpers. Outside a frame (a React effect on mount, a timer, an event handler) `write(fn)` runs at once, because half of today's writes happen there by design (`placePip` on mount, the static-scene `--p: 1`, the first reel position); what throws in dev is a read helper called during the write phase. Target: at most one style recalc and one layout per frame, and zero `Layout` events with a JS stack in the trace (§13).

Two startup fixes in the loop itself:

- `subscribeScrollFrame` calls `onLayout()` synchronously at subscribe time. About ten hooks subscribe inside one React effect pass, interleaved with style writes (`--p: 1`, `placePip`, the hero line's `getPointAtLength` / `getScreenCTM`), so the first second of the page pays several forced layouts while `word-rise` and `draw-once` are playing, on top of hydrating ~1 900 nodes in one task. The first `onLayout` is deferred to the read phase of the next frame, one layout for everyone; `relayout` (resize, fonts, the body `ResizeObserver`) likewise only marks the layout dirty and the measures run at the start of the next frame.
- The body `ResizeObserver` behind `relayout` fires on every body height change. With §9 skipping sections, a skip or unskip that moves `scrollHeight` by a few px would fire it on every scroll frame and cascade into every layout listener's measure; the probe counts `relayout` calls during the scroll scenario and the target is zero (the `contain-intrinsic-size: auto` values in §9 are what keeps the height stable).

The offenders and their fixes:

- `useMascotBrain`: Pip's width comes from a `ResizeObserver` on the element (set once, updated on resize), not `offsetWidth` per tick; `place(x)` goes through `write`. `useMascotControls.placePip` and `mascotPlacement.writePipPosition` are write-phase only.
- `useMascotAvoidance`: `visibleTargets` runs on the layout listener and when a zone enters or leaves (IntersectionObserver), caching document-space boxes; `onScroll` compares Pip's cached box against cached targets shifted by `scrollY`, measuring nothing. `onFocus` measures only on focus events.
- `useMascotGaze`: Pip's box is cached when a hold starts and refreshed on layout; the eye offset is written in the write phase.
- `usePointerHover`: `enterMagnetic` measures once on enter (and again on layout or scroll), `pullMagnetic` and `trackSurface` use the cached rect; writes go to the write phase.

## 7. SVG motion that the compositor can carry

In Chromium an animation whose target sits inside an `<svg>` is never composited (`kTargetHasInvalidCompositingState`), and `rotate` / `scale` / `translate` on any SVG element, root included, fails as `kSVGTargetHasIndependentTransformProperty`. A root `<svg>` animated through `transform` or `opacity` composites like any HTML element. So the continuous loops are rebuilt as **rigs**: an HTML box with absolutely positioned `<svg>` pieces, each animated on its own root through `transform` keyframes, `transform-origin` set on the piece (the hip, the leaf base, the wing root). One-shot acts (Pip's poke combos, the bird's pecks, the polaroid) may stay inside their SVG, since they are short and one at a time; the probe lists them as allowed exceptions (§13).

- **Pip** (`MascotArt` becomes `MascotFigure`; the name `MascotRig` is taken by the landing rigs of plan 5 §6, `MascotRig.tsx` and the `mascot-rigs` chunk): body, left leg, right leg, left arm, right arm, face as six `<svg>` roots inside `.figure` (`position: relative; width: var(--pip-width); aspect-ratio: 48 / 88`). The walk (`pip-step` on the legs, `pip-bob` on the body) and the idle breath move the pieces' roots. `[data-pip-part]` selectors keep their names, so `MascotActs.module.scss` changes only where an act animated a `<g>` that is now a root. The facing flip (`scale: -1 1` on `.art` today) moves to the `.figure` box. The mascot root loses `translate: var(--pip-x) var(--pip-y)` together with the three properties: `--pip-x`, `--pip-y` and `--pip-tilt` are unregistered today, so they inherit and every walk frame restyles Pip's 28 nodes (the 2.7 ms in §1); `writePipPosition` and `placePip` write `translate` and `rotate` on the root directly (rule 1), and the root loses `transition: transform` (rule 4: one transform-family property per element); the sticky-CTA lift (`transform: translateY(...)` today) moves to a wrapper element. The gaze offset (`--look-x` / `--look-y`) is written the same way, as `translate` on the eyes element.
- **Living mark** (`living-mark.tsx`): body and leaf as two `<svg>` roots in an inline-block `.mark` box. `breathe` becomes `transform: scale()` on the body root, `leaf-swing` `transform: rotate()` on the leaf root with `transform-origin: 10% 100%`. The outline-draw and fill-in stay inside (one-shot). The scroll lean (`--scroll-v`, `rotate` and its transition), `data-awake` and `--breath-delay` (`useSharedBreath`, whose ref becomes the box) apply to the box.
- **Bugs** (`bug.tsx`, used by the email field and the lens bug): body plus two leg `<svg>`s in an inline `.bug` box; `bug-step` / `bug-twitch` move the leg roots. The lens bug's host (`LensBug`) already moves an HTML element with direct `translate` / `rotate` writes, which stays.
- **Bird** (`CameraBird`): it is drawn **inside the render SVG** in phone coordinates (a `<g>` per bird, moved by inline `translate`, perched on the plateau and the flash), so its pieces cannot become roots without leaving the render. It stays where it is: `wing-flap` runs only during the flights (≈ 1 s, `infinite` while arriving or leaving, two beats on a ruffle), the hop, ruffle, tilt and peck are one-shots, and perched the bird is still, so all of them go on the allowlist as bounded acts. What changes is the glow filter around it (§8), which today re-rasterises the whole render on every wing beat.
- **Footer edge** (plan 5 §7): the wave strip becomes an HTML `.edge-wave` twice the viewport wide with the wave as a repeating `background-image` (SVG data URI, like `wave-mask`), moved by `transform: translateX(-tile)` (compositor, like `wave-drift`); the pulse window is a gradient-masked HTML strip translated across. The ruffle `scaleY` stays on the HTML `.edge`.
- **Hero words**: the hover lift uses an inner span (`.word-inner`) for `translate`, so the rise keyframes and the hover transition no longer share a target.
- **Hero line light, titanium band sweep, stroke draws**: `stroke-dashoffset` loops cannot composite, and neither can a `transform` loop on an SVG child. The band sweep (`band-sweep`, 7 s infinite, `transform` + `opacity` on the `.sweep` element inside the titanium `<svg>`) becomes an HTML gradient strip translated over the band inside the existing clip (same look as the titanium light sweep); the line light (`line-light`, 8 s, `opacity` + `stroke-dashoffset` on the hero line path) runs only while the hero is awake (already) and is accepted as the one main-thread loop at the hero, listed in the allowlist. ## 9. Layers, containment and skipping

- **Promotion rules** (rule 6): `will-change` only inside `when-awake` / `[data-near]` blocks; the mixin `promote-while-awake` wraps it so no bare `will-change` exists in the sources. Today nine declarations exist: five already gated (the backdrop waves, the exploded layers, the line-draw render, the hero visual, the living-surface wave) and four bare ones to move under the mixin (`LensBug`, `CameraBird`, `BackToTopFlight`, `RunawayLetters`, all `will-change: translate` for the life of the element). Stylelint has no rule that sees mixin scope, so the guard is a `config/willChange.test.ts` that compiles every module and asserts each `will-change` sits under a `[data-awake]`, `[data-near]`, `[data-visible]` or `[data-state]` selector.
- **Reveals** (`reveal` mixin on `view()`): every word, paragraph and card promoted for the page's life is the single biggest layer group (≈ 30 at the hero). Title words return to the IntersectionObserver path (`data-reveal` transitions, which end and demote), staggered by `--reveal-delay`. Cards and paragraphs keep the scroll-driven reveal but are **demoted once their range has passed**: `animationend` never fires for a scroll-driven animation, so one shared `IntersectionObserver` (the `useAwakeWhileInView` one, with a second threshold) sets `data-reveal="done"` when the block's top is above the range end, and the rule switches to `animation: none` with the end values. Zero reveal layers at rest; the attribute is also what `isSettled` reads (§5), so the `getAnimations()` question in §16 goes away. Layer count after this step is the first §14 checkpoint.
- **Backdrop**: the grain joins the root as a second `background-image` (one layer fewer); the tints shrink from 110 vmax to the viewport plus 20 % and are `contain: paint` clipped by the root; the blobs stay promoted (they move on scroll) but get `contain: paint` on the root so overlap does not promote the waves and the canvas. The canvas stays its own layer.
- **Overdraw**: the backdrop is one root layer (conic gradient plus grain), two blobs, two tints, the waves and the canvas, every one of them viewport sized; with the header, the pinned stages and the overlays, a pixel at the hero is composited about ten times. Budget: ≤ 5 viewport-sized layers at any scroll position on desktop, ≤ 3 on phones (§12), measured by the probe as the sum of layer areas over the viewport area (§13).
- **Sections**: `content-visibility: auto` on Hero's siblings and on the pinned sections, `contain-intrinsic-size: auto <height>` on **every** skippable section, explicit heights included, so a skipped section keeps its last laid-out size and the body `ResizeObserver` stays quiet (§5). The sticky stages keep working (sticky positioning is unaffected by layout containment; the stage's `overflow: clip` from plan 5 §13 stays). Anchor measuring for the particles (`measureAnchors`) and `documentTop` read boxes that containment does not change.
- **Isolation**: every ambient surface (`living-surface`, `sheen-host`) already has `isolation: isolate`; they gain `contain: paint` so a wave repaint never invalidates the card's neighbours.
- **Overlays**: the runaway-letters and mascot overlays stay `position: fixed`; their content is small. The A11y panel and sticky CTA are promoted only while open / visible (`will-change` under the panel's `[data-state]` open values / the CTA's `[data-visible]`). Pip's sticky-CTA lift today matches `body:has([data-sticky-cta][data-visible])` (`Mascot.module.scss`), a `:has()` anchored on `<body>`; the lift wrapper from §7 gets `data-lifted` from the sticky CTA through the request channel instead, so no rule anchors on the body.
- **Hit testing**: every pointer move hit-tests the DOM, and a decorative SVG with hundreds of paths under the pointer (the hero parts, the finishes render, the exploded stack) is tested path by path. Every `aria-hidden` decoration carries `pointer-events: none` (27 of 29 do today; the probe's `HitTest` sum shows the rest).

Budget (§14): ≤ 40 drawing layers at any scroll position on desktop, no layer larger than 1.5 × the viewport except the root scrolling layer.

## 17. Implementation notes

Filled in during the build. Where the build differs from the text above, the build is the rule.

- **Measuring.** Three probe mistakes looked like page problems. The trace's `RunTask` events include the GPU process, so the spec and the probe now count only `CrRendererMain` tasks: most "long tasks" in a scroll were `GPUTask`. A layout forced by the harness's own `scrollTo` (a stack whose top frame has no URL) is not the page's. Overdraw clips each layer's area to the viewport size, since the root scrolling layer is the whole document. The `perf` and `perf-mobile` projects run headed: headless Chromium rasterises in software and doubles the frame times. The trace names an animation's target and a failure bitmask, never the animation, so the allowlist (`e2e/perf-allowlist.ts`) lists main-thread properties, bounded-act targets and the transient "not composited yet" bits, which Chromium also reports for HTML spans when an awake loop restarts; an SVG child is never excused.
- **View timelines.** `view-timeline-inset: auto` takes the page's `scroll-padding-top` (the header, 76 px), which shifted every pinned range by 4–5 %; the pinned sections and the scrub paragraph set it to 0, and `--section-p` now equals `pinnedProgress` to four decimals.
- **Layers.** Chromium composites a scroll-driven `opacity` keyframe on an SVG path, and a scroll-driven animation never ends: the line drawing alone held 107 layers on every screen. Paths now animate only `stroke-dashoffset`, with a dash gap longer than the path so an undrawn round cap paints no dot and no opacity ramp is needed; the guides fade as one group; the exploded parts appear through a `visibility` step; the scrub words animate `color` toward a 50 % mix instead of `opacity`; the hero line light hides by moving its dash off the path. One-shots that end on their base style (`word-rise`, `draw-once`, the boot, the mark's draw and fill, the titanium callouts) fill `backwards` so they let go of their layer. Both pinned sections are `content-visibility: auto`. Hero layers went from 220 to about 44.
- **Forced style.** `window.scrollY`, `innerWidth` and `innerHeight` make Blink update style (and on a mobile viewport layout) before answering; after the frame's CSS animations that is a recalc per frame. Per-frame code reads `lastScrollY()` and `viewportSize()` from the frame loop. The letters' tick follows Pip through its inline `translate` (`createPipTracker`) instead of measuring it, and escapes are planned in the read phase of a frame (`readInNextFrame`), every glyph measured before any copy enters the overlay.
- **Selector cost.** A finish pick restyles the whole document once. The WCAG spacing rule's `:not(svg, svg *)` and the reduced-motion safety net's `:not(... [data-calm-fade] *)` walked every element's ancestors on every recalc, setting on or off; as `@scope (...) to (svg)` and `motion-reduce-scope('[data-calm-fade]')` the restyle went from about 89 to 52 ms. Skipped `content-visibility` subtrees still restyle on a root custom-property change (measured: removing the two pinned sections from rendering saved 26 ms, skipping them saved nothing), so the pick stays one 50–90 ms task.
- **Rigs (§7).** Pip has three pieces (two legs and a body with the face, arms and props inside), not six; the carry lean is a direct `rotate` on the figure and the rig art; the sticky-CTA lift is a wrapper inside the root, set from `data-lifted` by a MutationObserver on the bar. The mark's hover spin is an HTML box; the bug is three roots; the footer pulse is three nested boxes (window, counter-move, wave) so the accent wave travels with the grey one. A runaway letter's home follows its word only on a layout change, not per frame.
- **Reveals (§9).** `useReveal` sets `view` → `done` in the scroll-timeline branch (one IntersectionObserver at 60 % of the viewport) and `hidden` → `shown` → `done` on the transition path; titles take the transition path. `isSettled` reads only the attribute.
- **Not built.** The particle worker, the two-render cross-fade on a pick and Pip's walk as a Web Animation (§16) were not needed by the numbers; the formed shape's sway moved to a 30 ms timer so the loop sleeps between sways.
- **Budgets that moved** (`e2e/perf.spec.ts`, each a ratchet): idle recalcs ≤ 1.4 per frame (one from the CSS animations, plus the letters' and Pip's writes; 1.2 was the target); a forced layout may recur at most 10 times in 3 s (occasional one-off measurements stay, a per-frame one would show about 180); hero layers ≤ 48 (mobile 40), Inside ≤ 76 (90), Finishes ≤ 44 (42); hero overdraw ≤ 12.5 (9), against 5 (3); a finish pick's longest task ≤ 100 ms, against 50; at idle with Pip held the page may ask for two frames in 500 ms (the letters' escape poll). The reasons are in README "Known gaps".
